# PrizeVault architecture

## Components

| Component | Path | Role |
|---|---|---|
| Contract `prizevault` | `contracts/prizevault/src/lib.rs` | One Soroban contract instance hosting many tournaments: escrow, roster, ranking, payouts, refunds, events |
| Contract tests | `contracts/prizevault/src/test.rs`, `test_snapshots/` | 46 tests run in the Soroban host (`cargo test`): unit tests per function, negative auth/deadline tests, the 64-player scenario |
| CLI `prizevault` | `app/src/cli.ts` | Builds and (with an RPC) submits transactions through `contract.Client`; validates placement tables and results exports before anything is sent |
| Spec snapshot | `app/src/spec.json` | The wasm's `contractspecv0` section, base64; regenerated by `app/scripts/extract-spec.ts` so the client is constructed offline |
| Proof-of-funds page | `web/index.html` | Static HTML+JS; `simulateTransaction` of `status(id)` and `paid_out(id)` against any RPC, no wallet |
| Seed data | `data/seed/` | 64-player roster, 16-place table, invalid table, raw results export with a duplicate, corrected export, tournament parameters |
| Scripts | `scripts/build.sh`, `scripts/deploy-testnet.sh` | Local build/verify; testnet bootstrap (written, not executed here) |

Data flow: sponsor tokens -> contract (per-tournament accounting) -> winners (claims) / sponsor (refund). The CLI and page only ever talk to a Soroban RPC; there is no backend and no database.

## State machine

```
              create                      fund (any funder, <= pool_required)
  [none] ----------------> Created <------------------------------------------+
                              |                                               |
                              | open_registration (organizer; pool_funded == pool_required; now < register_by)
                              v
                            Open  <-- register (player; now < register_by)
                              |
                              | submit_results (organizer; register_by <= now < results_by; ranking valid)
                              |
              +---------------+-----------------+
              | referee == None                 | referee == Some
              v                                 v
          Confirmed  <---- confirm_results ---- ResultsSubmitted ---- reject_results ----> Open (registration stays closed)
              |            (referee; now < results_by)      ^                                (organizer resubmits)
              |                                             | submit_results again (organizer, replaces ranking)
              | claim (player; now < claim_by)              |
              |                                             |
              | refund_unclaimed (anyone; now >= claim_by)
              v
            Closed

  Created | Open | ResultsSubmitted --- cancel (organizer) -------------------------> Cancelled  (full refund to sponsor)
  Created | Open | ResultsSubmitted --- cancel_expired (anyone; now >= results_by) --> Cancelled  (full refund to sponsor)
```

Deadline semantics are uniform: "before X" means `now < X`, "after X" means `now >= X`, where `now` is the ledger close time. `create` requires `now < register_by < results_by < claim_by`. Consequences worth knowing:

- Once `results_by` passes, results can no longer be submitted **or confirmed**; the only exit is `cancel_expired`. This gives the sponsor a hard guarantee and removes any race between a late confirmation and an expiry refund.
- After a referee rejection the state is `Open` but `now >= register_by`, so nobody new can register; only the organizer's resubmission is possible.
- `Confirmed` is final: no cancel, no resubmission. Claims stop exactly at `claim_by`; from then on the sweep is deterministic (`pool_funded - paid_out`).

## Storage

All tournament data is **persistent** storage keyed by tournament id; the counter lives in **instance** storage.

| Key | Type | Written by |
|---|---|---|
| `Counter` (instance) | `u32` next id | `create` |
| `Tournament(id)` | `Tournament { organizer, sponsor, token, pool_required, pool_funded, placements: Vec<u32>, register_by, results_by, claim_by, referee: Option<Address>, state }` | every state change |
| `Roster(id)` | `Map<Address, bool>` | `register` |
| `Ranking(id)` | `Vec<Address>` first place first | `submit_results`; removed by `reject_results`, `cancel*` |
| `Claimable(id)` | `Map<Address, i128>` | confirmation; entries removed by `claim`; removed by `refund_unclaimed` |
| `Claimed(id)` | `Map<Address, i128>` | `claim` |
| `PaidOut(id)` | `i128` running total | `claim` |

Separate keys keep each transaction's write footprint small: a `claim` touches `Claimable`, `Claimed`, `PaidOut` and the token balances, never the roster.

### TTL

Every write goes through a helper that calls `extend_ttl(key, TTL_THRESHOLD, TTL_EXTEND_TO)` with `TTL_THRESHOLD = 30 days` and `TTL_EXTEND_TO = 120 days` in ledgers (17 280 ledgers/day at ~5 s). `create` also extends the instance TTL. A tournament that is touched at least once every ~90 days therefore never archives; one that is abandoned after `create` stays restorable (persistent entries archive, they are not deleted) and any later call, once the entry is restored through the transaction's restore footprint, extends it again. The test `ttl_is_extended_on_write` checks the extension on the tournament, roster, paid-out and instance entries.

## Authorization

| Function | `require_auth` | Extra preconditions | Errors |
|---|---|---|---|
| `create` | organizer | pool in `(0, MAX_POOL]`, placements valid, deadlines ordered | `InvalidAmount`, `InvalidPlacements`, `InvalidDeadlines` |
| `fund` | `from` (any address; nested token `transfer` auth) | state `Created`, `amount > 0`, `pool_funded + amount <= pool_required` | `InvalidState`, `InvalidAmount`, `Overfunded` |
| `open_registration` | organizer | state `Created`, fully funded, `now < register_by` | `InvalidState`, `Underfunded`, `RegistrationClosed` |
| `register` | player | state `Open`, `now < register_by`, not registered, roster < 1 024 | `InvalidState`, `RegistrationClosed`, `AlreadyRegistered`, `RosterFull` |
| `submit_results` | organizer | state `Open` or `ResultsSubmitted`, `register_by <= now < results_by`, `1 <= len <= placements.len()`, all registered, no duplicates | `InvalidState`, `RegistrationStillOpen`, `ResultsDeadlinePassed`, `InvalidRanking`, `NotRegistered`, `DuplicateInRanking` |
| `confirm_results` | referee | referee set, state `ResultsSubmitted`, `now < results_by` | `NoReferee`, `InvalidState`, `ResultsDeadlinePassed` |
| `reject_results` | referee | referee set, state `ResultsSubmitted` | `NoReferee`, `InvalidState` |
| `claim` | player | state `Confirmed`, `now < claim_by`, claimable > 0 | `InvalidState`, `ClaimWindowClosed`, `NothingToClaim` |
| `refund_unclaimed` | none | state `Confirmed`, `now >= claim_by` | `InvalidState`, `ClaimWindowOpen` |
| `cancel` | organizer | state in {Created, Open, ResultsSubmitted} | `InvalidState` |
| `cancel_expired` | none | `now >= results_by`, state in {Created, Open, ResultsSubmitted} | `ResultsDeadlineNotReached`, `InvalidState` |
| views: `status`, `claimable`, `claimed`, `paid_out`, `roster`, `is_registered`, `ranking`, `count` | none | | `NotFound` (status only) |

The contract itself is the `from` of every outgoing transfer (claims, refunds), so those need no external auth. The tests assert the exact auth trees with `env.auths()` (for example `fund` shows the funder's authorization with the nested token `transfer`), and every role check has a negative test that mocks the wrong signer with `mock_auths` or no signer at all.

## Payout math

`placement_amounts(pool, placements)`: for every placement except the last, `floor(pool * bps / 10_000)`; the last placement receives `pool - sum(previous)`. Properties: amounts always sum to `pool`; rounding dust (at most `placements.len() - 1` base units) lands on the last placement; no division by zero and no overflow because `pool <= i128::MAX / 10_000` and `bps <= 10_000`. Prizes are computed on `pool_funded`, which equals `pool_required` from `open_registration` onwards because `fund` refuses overfunding.

If the ranking is shorter than the table, unfilled placements' shares (including any dust attached to the last placement) are never assigned and go back to the sponsor in the sweep. The scenario test pins the numbers for a 7 777.7777777 USDC pool over 16 places: last place 583 333 340 base units (= 583 333 333 + 7 dust), 11 claims totalling 59 888 888 891, refund of exactly 17 888 888 886.

`app/src/placements.ts` and `web/index.html` mirror the same function in BigInt and are tested against the same constants.

## Events

Defined with `#[contractevent]`, so they are part of the contract spec. First topic is the snake_case event name, second the tournament id (plus the player for claims).

| Event | Data |
|---|---|
| `tournament_created` | organizer, sponsor, token, pool_required |
| `pool_funded` | from, amount, pool_funded |
| `registration_opened` | pool_funded |
| `player_registered` | player, roster_size |
| `results_submitted` | ranking_len, needs_referee |
| `results_confirmed` | ranking_len, payable_total |
| `results_rejected` | - |
| `prize_claimed` (topic: player) | amount |
| `unclaimed_refunded` | sponsor, amount |
| `tournament_cancelled` | refunded, expired |

## Trust assumptions and failure modes

- **Organizer disappears** before opening or before submitting results: after `results_by` anyone can `cancel_expired`; the sponsor is refunded in full.
- **Referee disappears**: same; results that are never confirmed expire into a refund. Sponsors and organizers should pick `results_by` with enough slack for the referee.
- **Wrong results submitted**: the referee rejects and the organizer resubmits; without a referee the organizer's submission is final, which the proof-of-funds page shows (`referee: none`).
- **Winner never claims**: their share goes back to the sponsor at `claim_by`. There is no way to redirect a prize to a different address; players must register with the address they can sign for.
- **Co-funders**: anyone can `fund`, but every refund goes to the recorded `sponsor`. Co-funders trust the sponsor.
- **Token**: any SEP-41 token works. For classic assets wrapped as Stellar Asset Contracts, G-accounts need a trustline before they can receive a claim; the CLI cannot detect this in advance (the claim transaction fails in simulation).
- **No admin**: nothing can pause, upgrade or drain the contract; the trade-off is that a bug needs a redeploy with new tournaments.
- **Clock**: deadlines use ledger close time; validators keep it within seconds of wall time.

## Limits

- `MAX_PLACEMENTS = 256`, `MAX_ROSTER = 1 024`: keeps every entry far below the 64–128 KiB ledger-entry ceiling and `submit_results` under the per-transaction instruction budget (roster lookups and duplicate detection are map operations, not linear scans).
- `MAX_POOL = i128::MAX / 10_000` base units.
- One ranking per tournament; ties must be expressed as consecutive places with equal bps (the seed table does exactly that).
- Wasm: 20 384 bytes optimized, 19 exported functions, hash `70b9c643ad18c788b8bed4334b033934208536ac7d6d29566c6881e9ab53bce1`.

## App design

- `contract.Client` is constructed from `spec.json` (`new contract.Spec(base64)`), so argument encoding is spec-driven and typed; `Client.from`'s RPC fetch of the wasm is unnecessary. Read-only commands simulate with the SDK's null account; mutating commands sign with `basicNodeSigner` and `signAndSend`.
- `app/src/invoke.ts` builds the same `InvokeHostFunction` transactions without any RPC (used by the offline tests and mirrored by the web page).
- `results.ts` reproduces the contract's ranking rules (empty, too long, duplicate, unregistered) and the structural ones the contract cannot see (place gaps, invalid strkeys, whitespace), and reports all of them at once with row numbers.
- `proof.ts` normalises the three shapes the SDK uses for the `State` enum (`"Open"`, `["Open"]`, `{ tag: "Open" }`) and renders the shareable summary.
- The web page uses the SDK's browser bundle from a CDN and needs the RPC to allow cross-origin requests (the SDF testnet RPC does).

## Why Stellar

The value of the product is that a promise ("the pool is funded") becomes verifiable and the release rule is enforced by code rather than by the organiser's cash position. Stellar fits the specific users: native USDC and other dollar stablecoins, sub-cent fees for paying 64–256 placements, anchors and MoneyGram cash-out in LatAm, SEA and MENA where tier-2 teams live, and cheap accounts for players who do not have a wallet yet (`research/01-stellar-ecosystem.md`, `research/08-final-selection.md` §01). An Arbitrum/Xai route would require EVM wallets from non-crypto teams and offers no cash-out edge. No AI component: results come from bracket tools and referees.
